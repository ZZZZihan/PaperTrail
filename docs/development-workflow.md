最新阶段已解除旧累计上限的阻塞，继续真实开发验证。QA v5 的完整旧 15 题独立核对为 7/10 完整有据交付、16/18 原要点、10/11 必要条件、79/80 原子事实有据；检索充分性为 10/10，仍存在正文遗漏、额外背景误判和范围过度断言。简介 v8 三篇均未通过发布检查，旧成功缓存继续可读。实际版本、分轮结果、检查和未完成项统一见 [v0.2 验证记录](verification-quality-v02.md)；这些是开发诊断，人工产品与学习验收仍待本人反馈。

本轮规格与设计依据用户的持续开发授权形成，公开 Agent 论文开发样例由 AI 准备、待人工核对。模型采用显式授权的 `provider_quota` 模式，沿同一 scope 持久累计调用；未知费率与实际费用保持未知，不能把调用配额换算成金额。前两轮运行及失败证据保留，不替换为第三轮成绩。继续以 [当前质量规格](reading-quality-v02.md) 和 [简短人工清单](manual-trial-v02.md) 区分工程/开发验证与用户产品/学习验收；原 P0 的真实阅读需求、人工样例及验收仍为 pending，不能因等待这些材料暂停其他已获授权工作，也不能用模拟回答替代真实模型验证。

## 本次固化的决定

沿用此前 v0.1 项目与流程讨论的产品范围和 P0—P5 路线，完整产品基线见 [项目与学习基线](project-baseline.md)。正式研发文档在 [ZZZZihan/PaperTrail](https://github.com/ZZZZihan/PaperTrail) 维护，任务状态与依赖在 [Linear](https://linear.app/colife/project/papertrail-论文研读-agent-93a0ba2ee811) 维护。本轮已形成限定于单篇论文证据问答的行为规格、设计和 AI 开发样例；这些产出不替代 COL-10—COL-14 原有的人工需求、样例与验收，也不意味着原 P0 任务全部完成。

PaperTrail 是论文研读 Agent 求职项目；mypaper 用于论文选题、开题和发表，RepoPilot 是另一个工程项目。

## 一项功能的完整流程

| 步骤 | 最小产出 | 推进依据 |
| -- | -- | -- |
| 理解问题 | 真实阅读经历、用户和当前解决方式 | 可以说明具体困难及改善价值 |
| 明确需求与范围 | 用户故事、输入输出、主流程、异常与暂缓项 | 能区分本轮交付与后续候选 |
| 定义验收与样例 | 人工证据、可观察的验收条件与评分规则 | 成功、证据不足、失败都有定义 |
| 设计交互与方案 | 页面草图、数据流、技术取舍、待验证假设 | 正常和重要异常可走查，模型与程序职责清楚 |
| 拆分任务 | 产出、依赖、验收办法与学习目标 | 首项工作具体且能独立验证 |
| 实现与持续验证 | 小步提交、必要测试与 AI 评测 | 改动对应已定义的需求或缺陷 |
| 审查与整体验收 | 演示、审查结论、当前版本验证证据 | 预设标准满足，限制如实记录 |
| 发布与运行 | 发布记录、启动检查、日志和回退办法 | 目标用户可以完成任务，故障可定位 |
| 反馈与下一轮 | 失败案例、优先级和新任务 | 围绕真实瓶颈提出可验证改动 |

上述步骤定义需要留下的证据，不要求在用户已授权持续开发时逐项停下征求确认。需要代码试验的事项先记录假设、输入、成功或失败判据，再按授权推进；规格与设计可随实施更新。小型文案与样式调整可以在一项任务里写清改动和检查；关键新行为、数据结构和 Agent 逻辑展开设计与评测。缺少真实阅读材料时，集中记录人工依赖，并继续不依赖它们的工作。

## 信息归属

* Linear Project：目标、范围、当前阶段和路线。
* Linear Milestone：阶段成果及完成条件。
* Linear Issue：具体工作、依赖、状态、学习目标与完成证据。
* GitHub 文档：正式规格、设计、开发约定和评测说明。
* GitHub PR：实际改动、审查和验证结果。

任务链接到规格，PR 链接到任务。同一任务只在 Linear 维护状态。本文件作为后续流程变更的维护入口；[Linear v0.2 文档](https://linear.app/colife/document/papertrail-开发流程与协作约定-v02-791624f10e5a)保留为交接前的试行记录。任务快照标明日期，不替代实时状态。

## 状态与推进条件

沿用现有 CoLife 团队状态：
Backlog（待整理）→ Todo（可开始）→ In Progress（进行中）→ In Review（待验收）→ Done（已完成）。

受阻用 blockedBy 依赖和任务中的阻塞原因、解除条件表达。个人学习阶段同时推进一个主要任务。

可开始：目标与范围清楚、验收办法已写下、依赖具备；验证假设的任务需有明确判据。
已完成：实际产出符合验收；必要的正常、异常和边界已验证；涉及模型行为的改动有相关评测；记录当前提交或文档版本、实际结果与限制。
代码审查通过、功能验收通过、已发布分别记录，不能相互替代。文档任务不强行要求代码测试；未运行的评测不能填写为通过。

## 软件验证、AI 评测与学习验收

引用能打开属于软件行为；引用是否支持答案属于语义质量。两者分别核对。
从需求阶段准备人工样例，从第一次模型调用开始记录模型与提示配置、输入输出、调用量、耗时、错误及可获得的费用。无费用数据标记未知。
当前 3 篇论文、15 题为 AI 准备并已用于多轮调试的开发诊断集，真实模型结果与独立 AI 审查见 [逐题结果](../evals/development-v0.1/results-2026-09-05.json)。它不替代原 P0 人工样例，也不是未见过的泛化测试集；P2 的初始阈值不能据此自动记为产品验收通过。展示阶段另建未用于调试的问题集，并报告样本数与限制。
助手负责解释、拆分、按任务实施、审查和定位问题；学生仍需掌握核心实现，亲手修改并验证关键逻辑，解释输入输出、设计理由与失败案例。每个学习里程碑保留演示、技术取舍、实测结果及失败改进案例。

## 可复用任务模板

### 目的与范围

哪个真实问题值得解决？本轮交付哪些行为，暂缓哪些候选？

### 输入与输出

需要哪些资料或前置成果？形成什么可检查的产出？

### 验收条件

给定什么情境，执行什么操作，应出现什么结果？

### 依赖与设计

关联规格、关键取舍、前置任务、阻塞原因和解除条件。

### 学习目标

本次理解的 1—3 个核心概念。

### 验证与完成证据

适用的人工检查、软件测试、AI 评测；实际结果、文档或提交版本、PR 或演示链接、已知限制。未完成时明确留待填写。

## 继续项目时如何工作

先看当前里程碑、进行中的任务和最近验证结果。汇报当前状态、阻塞、下一项具体动作。新想法进入 Backlog，经优先级评估后再影响本轮范围。
复盘应区分计划、进行中与已验证成果；若没有新证据，说明信息缺口。按实际阶段推进，不自动把讨论任务变成代码实施任务。
