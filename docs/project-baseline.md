## 1. 我们要达成的目标

围绕自己读 LLM / Agent 论文时遇到的真实问题，逐步做出可以使用、解释、评测和部署的应用，形成 Agent 全栈开发的求职作品。

用户已确定：以南开就业网发布的天津小橙集团「AI Agent 开发工程师（AI Native 方向）」岗位作为核心能力参照。岗位发布于 2026-06-29；沿用此前讨论的岗位核对，本轮没有重新开展岗位调研。

岗位重点可概括为：完整项目交付与设计解释、编程和后端基础、Agent 与工具调用、RAG、评测与运行追踪、部署工程，以及对实际效果负责。以下范围、架构、阶段和指标均为本项目的教学设计，不是该公司的官方验收标准，也不代表达到后即可获得录用。[岗位原文](https://career.nankai.edu.cn/correcruit/content/id/116181.html)

最终应有两类证据：产品能完成真实任务；开发者能独立解释、修改并验证核心实现。

## 2. 产品定义和第一个用户故事

目标用户先聚焦本人，后续邀请少量同学试用。核心场景是阅读、理解和比较 LLM / Agent 论文。

**用户故事：**作为正在读论文的研究生，我希望上传论文并提出一个研究问题，得到带原文依据的回答，能直接检查关键结论来自哪里，从而减少反复翻找原文的时间。

第一版交付：单篇论文的证据问答。后续扩展：围绕明确问题，对 2—5 篇论文的方法、实验条件和局限进行比较。

用户最终看到的是：答案、支撑答案的原文片段、PDF 页码，以及证据不足的提示。比较结果必须保留实验条件；条件不一致时说明比较限制。

“AI Native”在本项目里的操作性定义：任务需要模型理解问题、判断已找到的证据是否足够，并在受控范围内选择下一步；任务状态、工具结果、证据与失败记录作为产品数据保存。文件存储、权限、格式校验等确定性工作由普通程序负责。

## 4. 第一版范围与行为约定

### 输入和输出

- 输入：一篇可提取正文的 PDF，加一个自然语言问题。
- 输出：回答、对应证据、PDF 页码和任务状态。
- 输入范围先限定为可提取文本的论文；扫描件、复杂图表和公式识别按实际失败样例安排后续支持。
- 任务失败要给出用户可理解的原因和下一步；空正文不能当作解析成功。

### 证据约定

- 每个关键事实结论绑定至少一个证据片段；事实、作者观点和系统推断分别标明。
- 证据保存论文标识、文件哈希、片段标识和 PDF 物理页索引。显示页码使用索引加一；印刷页码与物理页码可能不同。
- 引用从系统检索返回的标识中选择，程序检查标识存在且属于当前用户可访问的论文。
- 引用存在只证明“找得到这段话”；是否真正支持结论还需语义评测和人工抽查。
- 没找到依据时表达为“在当前已检索证据中未找到支持”，避免把未检索到误写成论文中必然不存在。

### Agent 的逐步引入

先完成固定流程基线：解析、检索、生成、引用校验。需要处理证据缺口时，再加入单 Agent 的受限循环：检索、读片段、检查信息是否足够、补检索或结束。

后续 Agent 的候选工具先限定为 search_passages 和 read_passage，多篇比较时再加入文档筛选。原基线建议 6 次工具调用、120 秒任务时限及取消能力，这些尚未实现，需届时测量后确定；当前 v0.1 采用固定流程、最多 3 次模型调用和 180 秒处理期限。

文档里的文字按待分析资料处理。它不能改变工具权限或触发外部操作。对外部写入能力的需求出现后，另行设计权限与确认流程。

## 5. 当前技术与后续引入条件

| 部分 | v0.1 实际选择 | 后续引入条件 |
| --- | --- | --- |
| 后端 | Python、FastAPI、类型化请求与响应 | 按实际并发与部署需求拆分；[官方文档](https://fastapi.tiangolo.com/) |
| 业务数据与检索 | PostgreSQL 17、pypdf、页内分块、查询转换与 BM25 | 向量/混合检索需在冻结样例上证明收益，再评估 [pgvector](https://github.com/pgvector/pgvector) |
| 模型调用 | OpenAI 兼容接口、结构化回答、程序引用校验、单独模型支持检查 | 固定模型、提示、用量与成本来源；按实际服务能力调整参数 |
| Agent 编排 | 固定查询、检索、生成和检查，没有自主工具循环 | 需要补检索且比较有益后再引入受控 Agent；[LangGraph 官方概览](https://docs.langchain.com/oss/python/langgraph/overview) 仅为后续参考 |
| 前端 | TypeScript、React、PDF.js，论文/问答/证据视图 | 按用户试用发现的操作问题改进 |
| 运行追踪 | 持久任务/调用账本、每次诊断独立产物和哈希 | 需要集中跨服务观察时再评估 [Langfuse](https://langfuse.com/docs) |
| 交付 | uv、Make、本地 PostgreSQL 管理脚本与 CI 工作流 | 容器、公网部署、多用户认证与隔离留待真实发布目标 |

当前采用模块化单体，文件与数据库保存在本地持久目录。问答状态持久保存，浏览器断线不决定后台任务是否继续；应用重启将未完成任务记为中断，不自动再调用模型。跨机器存储、独立任务执行进程与更复杂恢复根据后续部署需求引入。

本轮 16 个预期证据定位片段，原中文问题的 BM25 检索命中 10 个，查询转换后命中 15 个。这个对照解释了当前查询转换的选择；本轮没有测试向量检索，不能声称 BM25 优于向量方案。具体配置、来源和限制见 [开发诊断说明](development-diagnostics.md)。

真实模型、密钥与本轮配额已在本机配置，按现有授权继续试用。费用未知时如实保留未知，不能使用其他模型价格代替；其他机器的配置与可复现启动见 [本地开发说明](local-development.md)。公网部署环境仍属后续待定事项。

多 Agent、知识图谱、微调、语音、Kubernetes 等作为扩展候选。只有出现具体瓶颈、存在可比较的基线，并能说明预期收益时，才进入实施范围。

按验收推进，不预先承诺几周完成。本轮已形成工程规格、AI 开发样例、实际代码与真实模型诊断；P0 的真实阅读需求、人工样例和评审继续待完成。工程交付不自动推进原 P0 人工任务，也不替用户填写已掌握。

单用户本地开发可先使用开发身份；允许多人访问前必须完成身份校验与论文、任务、证据的数据隔离。恢复从已持久化的边界继续；外部模型请求是否发生过可能存在不确定性，重复调用和潜在重复计费需要可见。

## 7. 评测方法和首轮验收

下列数字保留项目最初的人工验收目标。当前公开开发集已有上方列出的真实模型与独立 AI 诊断结果，但尚未完成人工效果验收，不能把 AI 完整题数直接填写成人工认可题数。

### 启动样例

原 P0 人工样例要求：选择 3 篇本人实际需要阅读、正文可提取的论文。人工整理 15 个问题：10 个在论文里有明确依据，5 个在给定资料范围内无法支持。每题保存问题、允许使用的论文、预期结论或证据不足原因，以及人工核对过的页码和片段。

问题模板包括：研究问题是什么、方法的关键步骤是什么、某个实验结论成立于什么设置、作者承认了哪些局限、论文是否支持一个刻意设置的过度概括。模板必须改写为针对具体论文的题目，不能直接当作已标注数据。当前 [公开开发集](development-diagnostics.md) 的 3 篇 15 题由 AI 准备并参与调试，用户阅读经历与逐题人工核对仍待补充。

### P2 首轮目标

- 15 个样例都能够结束并返回明确状态，失败和证据不足也属于有定义的状态。
- 在 10 个可回答问题中，至少 8 个给出人工认可且有证据支撑的关键答案。
- 5 个不可回答问题都正确提示证据不足，不编造页码或来源。
- 所有返回的引用标识能通过程序校验；人工逐条核对结论与证据关系。
- 输出逐题结果、失败原因、模型配置、提示版本、调用量、用时和可获得的费用记录。

这 15 题用于开发与诊断，结果只描述这组样例。准备求职展示前，另建至少 20 道未参与调试的题，覆盖新论文并提前固定评分规则；若使用这些题继续调参，就需另建评测集。小样本结果不写成通用准确率。

### 对比方案

在全文能放入同一模型上下文的样例上，比较直接输入全文、固定检索和 Agent 三种方案。固定资料、问题、模型、评分规则，并报告实际输入长度与资源预算；不适用的样例单独说明。Agent 若无明显收益或资源代价过高，就保留更合适的流程并解释选择。

自动模型评分可以辅助筛查；关键结论与证据的验收保留人工核对。确定性测试覆盖引用归属、权限、工具参数、任务限步和恢复等关键边界；质量问题通过评测样例验证。

## 8. 学习协作方式

每个功能按以下顺序推进：明确一个用户问题，讲清必要原理，完成学生可理解的最小实现，进行代码审查，运行相关样例，记录设计决策和失败。用户已安排后续由 Codex 接手开发；AI 可承担实现，学生仍需亲手修改并验证核心逻辑。

助手负责拆解需求、讲解原理、按任务实施、审查代码和帮助定位问题。学生需要亲自解释输入输出、状态与错误处理，修改核心逻辑，并用结果证明理解。已熟悉的部分可加快，薄弱部分通过小练习补齐。

每阶段沉淀四项：可运行功能、设计决策记录、验证结果、能独立回答的原理问题。提交历史如实标明本人工作与 AI 辅助范围；简历只使用可复现的实测结果。

## 9. 下一项人工与学习任务

当前工程已可供试用，用户下一步按 [约 25 分钟人工清单](manual-trial-v01.md) 完成主流程、证据核对与反馈。原 [COL-10：用一次真实阅读经历核实首版产品需求](https://linear.app/colife/issue/COL-10/用一次真实阅读经历核实首版产品需求) 仍需本人提供事实；COL-11/13 可基于已实现的规格与设计核对原任务验收，COL-12 的人工样例及 COL-14 的 P0 评审与学习复述继续保留。

阅读样例的交付格式不变：选择一篇自己确实需要阅读的论文，写下一个真实问题，人工找到答案和原文页码，再写一个当前资料无法支持的问题。将真实卡点与已有问答行为对照，判断下一轮应改进什么，不编造阅读经历补齐材料。

用户需要能解释：文件怎样成为可检索的数据；检索出来的一段话为什么可能不支持答案；为什么 AI 开发诊断不等于人工效果验收；哪些步骤适合普通代码，哪些步骤需要模型判断。之后亲手修改一项核心参数或逻辑并运行对应验证，单独留下学习证据。

人工产品验收句：上传论文并提问后，系统返回可核对的答案和证据；证据不足、解析失败或任务超时都有明确状态，用户能理解接下来该做什么。
