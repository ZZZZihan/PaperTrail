## 1. 我们要达成的目标

围绕自己读 LLM / Agent 论文时遇到的真实问题，逐步做出可以使用、解释、评测和部署的应用，形成 Agent 全栈开发的求职作品。

用户已确定：以南开就业网发布的天津小橙集团「AI Agent 开发工程师（AI Native 方向）」岗位作为核心能力参照。岗位发布于 2026-06-29，本次于 2026-09-05 核对。

岗位重点可概括为：完整项目交付与设计解释、编程和后端基础、Agent 与工具调用、RAG、评测与运行追踪、部署工程，以及对实际效果负责。以下范围、架构、阶段和指标均为本项目的教学设计，不是该公司的官方验收标准，也不代表达到后即可获得录用。[岗位原文](https://career.nankai.edu.cn/correcruit/content/id/116181.html)

最终应有两类证据：产品能完成真实任务；开发者能独立解释、修改并验证核心实现。

## 2. 产品定义和第一个用户故事

目标用户先聚焦本人，后续邀请少量同学试用。核心场景是阅读、理解和比较 LLM / Agent 论文。

**用户故事：**作为正在读论文的研究生，我希望上传论文并提出一个研究问题，得到带原文依据的回答，能直接检查关键结论来自哪里，从而减少反复翻找原文的时间。

第一版交付：单篇论文的证据问答。后续扩展：围绕明确问题，对 2—5 篇论文的方法、实验条件和局限进行比较。

用户最终看到的是：答案、支撑答案的原文片段、PDF 页码，以及证据不足的提示。比较结果必须保留实验条件；条件不一致时说明比较限制。

“AI Native”在本项目里的操作性定义：任务需要模型理解问题、判断已找到的证据是否足够，并在受控范围内选择下一步；任务状态、工具结果、证据与失败记录作为产品数据保存。文件存储、权限、格式校验等确定性工作由普通程序负责。

| 能力目标 | 在项目中做什么 | 能留下什么证据 |
| --- | --- | --- |
| 后端与数据建模 | 上传论文、查询任务、保存会话和证据 | API 契约、数据库迁移、错误处理示例 |

| 评测与优化 | 比较直接读全文、固定检索和 Agent 方案 | 同条件的质量、调用量、耗时对照 |

## 4. 第一版范围与行为约定

### 输入和输出

- 输入：一篇可提取正文的 PDF，加一个自然语言问题。
- 输出：回答、对应证据、PDF 页码和任务状态。
- 输入范围先限定为可提取文本的论文；扫描件、复杂图表和公式识别按实际失败样例安排后续支持。
- 任务失败要给出用户可理解的原因和下一步；空正文不能当作解析成功。

### 证据约定

- 每个关键事实结论绑定至少一个证据片段；事实、作者观点和系统推断分别标明。
- 证据保存论文标识、文件哈希、片段标识和 PDF 物理页索引。显示页码使用索引加一；印刷页码与物理页码可能不同。
- 引用从系统检索返回的标识中选择，程序检查标识存在且属于当前用户可访问的论文。
- 引用存在只证明“找得到这段话”；是否真正支持结论还需语义评测和人工抽查。
- 没找到依据时表达为“在当前已检索证据中未找到支持”，避免把未检索到误写成论文中必然不存在。

### Agent 的逐步引入

先完成固定流程基线：解析、检索、生成、引用校验。需要处理证据缺口时，再加入单 Agent 的受限循环：检索、读片段、检查信息是否足够、补检索或结束。

工具最初只需 search_passages 和 read_passage；多篇比较时再加入文档筛选。初始可配置上限为 6 次工具调用、120 秒任务时限，同时支持取消；这些是工程起点，待测量后调整。

文档里的文字按待分析资料处理。它不能改变工具权限或触发外部操作。对外部写入能力的需求出现后，另行设计权限与确认流程。

## 5. 技术起点与引入条件

| 部分 | 建议起点 | 引入理由或条件 |
| --- | --- | --- |
| 后端 | Python、FastAPI、类型化请求与响应 | 先掌握 HTTP、数据校验和服务边界；[官方文档](https://fastapi.tiangolo.com/) |
| 业务数据与检索 | PostgreSQL，向量检索阶段加入 pgvector | 先把论文、片段和任务关系建清楚；pgvector 提供 Postgres 向量检索能力；[项目文档](https://github.com/pgvector/pgvector) |
| 模型调用 | 接口封装、结构化输出、错误记录 | 模型配置可替换；固定评测时记录模型与参数 |
| Agent 编排 | 先理解工具循环，再用 LangGraph 管理状态 | 需要检查点、暂停和恢复时引入；[官方概览](https://docs.langchain.com/oss/python/langgraph/overview) |
| 前端 | TypeScript、React | 先做论文、问答、证据三个核心视图；界面版本在初始化时确认 |
| 运行追踪 | 初期结构化日志，后续接入 Langfuse | 需要集中查看多步调用和评测时引入；[官方文档](https://langfuse.com/docs) |
| 交付 | Docker Compose、持续集成 | 在清洁环境复现核心流程 |

先按模块化单体组织。文件先存开发环境的持久卷；有跨机器部署需求时接入对象存储。长任务进入部署阶段前使用持久任务状态与独立执行进程，浏览器断线不应决定任务是否继续。

模型服务、密钥、预算和部署环境尚未确定；开始付费模型调用或外部部署前再依据实际可用条件配置。模型费用记录实际用量和计价版本；缺失时标记未知，不写成零成本。

多 Agent、知识图谱、微调、语音、Kubernetes 等作为扩展候选。只有出现具体瓶颈、存在可比较的基线，并能说明预期收益时，才进入实施范围。

## 7. 评测方法和首轮验收

下列数字是项目的初始目标，尚无实测结果。

### 启动样例

选择 3 篇本人实际需要阅读、正文可提取的论文。人工整理 15 个问题：10 个在论文里有明确依据，5 个在给定资料范围内无法支持。每题保存问题、允许使用的论文、预期结论或证据不足原因，以及人工核对过的页码和片段。

问题模板包括：研究问题是什么、方法的关键步骤是什么、某个实验结论成立于什么设置、作者承认了哪些局限、论文是否支持一个刻意设置的过度概括。模板必须改写为针对具体论文的题目，不能直接当作已标注数据。

### P2 首轮目标

- 15 个样例都能够结束并返回明确状态，失败和证据不足也属于有定义的状态。
- 在 10 个可回答问题中，至少 8 个给出人工认可且有证据支撑的关键答案。
- 5 个不可回答问题都正确提示证据不足，不编造页码或来源。
- 所有返回的引用标识能通过程序校验；人工逐条核对结论与证据关系。
- 输出逐题结果、失败原因、模型配置、提示版本、调用量、用时和可获得的费用记录。

这 15 题用于开发与诊断，结果只描述这组样例。准备求职展示前，另建至少 20 道未参与调试的题，覆盖新论文并提前固定评分规则；若使用这些题继续调参，就需另建评测集。小样本结果不写成通用准确率。

### 对比方案

在全文能放入同一模型上下文的样例上，比较直接输入全文、固定检索和 Agent 三种方案。固定资料、问题、模型、评分规则，并报告实际输入长度与资源预算；不适用的样例单独说明。Agent 若无明显收益或资源代价过高，就保留更合适的流程并解释选择。

自动模型评分可以辅助筛查；关键结论与证据的验收保留人工核对。确定性测试覆盖引用归属、权限、工具参数、任务限步和恢复等关键边界；质量问题通过评测样例验证。

## 8. 学习协作方式

每个功能按以下顺序推进：明确一个用户问题，讲清必要原理，完成学生可理解的最小实现，进行代码审查，运行相关样例，记录设计决策和失败。用户已安排后续由 Codex 接手开发；AI 可承担实现，学生仍需亲手修改并验证核心逻辑。

助手负责拆解需求、讲解原理、按任务实施、审查代码和帮助定位问题。学生需要亲自解释输入输出、状态与错误处理，修改核心逻辑，并用结果证明理解。已熟悉的部分可加快，薄弱部分通过小练习补齐。

每阶段沉淀四项：可运行功能、设计决策记录、验证结果、能独立回答的原理问题。提交历史如实标明本人工作与 AI 辅助范围；简历只使用可复现的实测结果。

## 9. 第一项具体任务

当前任务：[COL-10：用一次真实阅读经历核实首版产品需求](https://linear.app/colife/issue/COL-10/用一次真实阅读经历核实首版产品需求)。目的仍是定义一条可验收的论文证据问答。COL-11 接续完成正式功能规格与评分规则。

交付格式：选择一篇论文、写下一个真实问题、人工找到答案和原文页码、再写一个该论文无法回答的问题。先用这两题明确产品在成功与证据不足时分别应该做什么，再进入上传和解析实现。

第一课要能解释：文件怎样成为可检索的数据；检索出来的一段话为什么可能不支持答案；为什么需要在生成前准备人工证据；哪些步骤适合普通代码，哪些步骤需要模型判断。

第一阶段验收句：上传论文并提问后，系统返回可核对的答案和证据；证据不足、解析失败或任务超时都有明确状态，用户能理解接下来该做什么。
